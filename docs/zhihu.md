# 用 Rust 写了一个被动式 SIP/RTP 语音质量监控工具 sipmon

> 面向知乎读者:这篇侧重**怎么实现**和**性能/内存怎么优化**。想看功能概览可看另一篇(见文末链接)。

## 为什么做这个

排查 VoIP / 语音通话质量问题(卡顿、断续、听不清)时,常见的做法是登录 PBX 看日志,或者把抓包文件下载回来再打开 Wireshark 慢慢翻。问题是:

- PBX 侧的日志看不到**真实媒体路径**(尤其经过 TURN 中继时);
- 事后抓包分析没有实时性,故障现场已经过去;
- 团队里不是人人会用 Wireshark 的过滤器和统计视图。

所以我想做一个**被动式、旁路部署**的监控工具:部署在镜像口/分流口的抓包机上,**不依赖运行中的 PBX**,一边抓一边在 TUI 里实时展示"每通电话质量如何、哪个 IP 丢包最严重、告警规则命中了几条",抓完还能导出 JSONL 做后续分析。

项目地址:`https://github.com/miuda-ai/sipmon`(crates.io 上有 `sipmon` 0.1.3)。

## 整体架构

单二进制,双线程模型:

```
┌─────────────┐      ┌───────────────────────────────┐
│ 主线程:TUI   │◄────►│  共享快照 Snapshot (Arc<Mutex>)│
└─────────────┘      └───────────────▲───────────────┘
                                     │ 100ms 增量发布
┌─────────────┐      ┌───────────────┴───────────────┐
│ 工作线程:     │      │  Correlator 关联器             │
│ 抓包 → 解码    │────►│  SIP 状态机 / RTP 统计 / 诊断规则 │
└─────────────┘      └───────────────────────────────┘
```

- **输入抽象成 `CaptureSource` trait**:libpcap 网卡(带 BPF)、离线 pcap/pcapng、stdin 的 `tcpdump -w -` 流、以及历史事件日志(evlog)回放,统一成"下一帧"的迭代器,上层代码完全不用关心来源。
- **解码链路**:`etherparse` 解 IP/UDP → 按载荷分类(SIP/RTP/RTCP/STUN)→ 交给对应解析器。SIP 的解析复用 `rsipstack`(只取解析器和报文模型,不碰网络栈)。
- **关联器(核心)**:以 Call-ID 为纲维护呼叫状态机;SIP 事务按 `branch + method` 关联;媒体流通过 **SDP 协商的端点**做关联——两张 O(1) 的 `endpoint_call` 哈希表把"五元组 → 呼叫"直接钉死,包进来不用线性搜索。
- **媒体质量**:RFC3550 抖动/丢包统计(64 包重排窗口)、RTCP RR 的 LSR/DLSR 算 RTT、单向时延估计、以及简化 E-model(ITU-T G.107)算 MOS。
- **TURN 自动学习**:从 STUN/Data indication 自动发现 TURN 服务器,给中继腿打上 `turn-client` / `turn-peer` 标签,一眼看出通话有没有绕远路。
- **诊断规则引擎**:20+ 条规则(Contact 可达性、Record-Route、SDP/RTP 一致性、单向媒体、TURN allocation/refresh 等),按 warn/critical 分级。

## 性能与内存优化(重点)

做被动监控,最怕的就是**长时间挂着跑爆内存**或者**把业务链路拖垮**。所以设计上有几个硬约束:

1. **一切有界,能淘汰就淘汰**
   - 呼叫、流、诊断全部是**环形/可淘汰结构**:默认 `--max-calls 100000`、`--max-streams 50000`、`--max-diagnostics 50000`,满了淘汰最老的已结束呼叫。跑一周也不会无界增长。
   - 单呼叫内报文有上限(2000 条),长活呼叫不会把内存吃成无底洞。

2. **时间窗不用存历史包,用固定桶求和**
   - 每个 IP 维护两级滚动桶:**1s × 600(10 分钟)+ 1m × 60(1 小时)**。
   - 界面上的丢包率窗口(1s/5s/10s/20s/1m/10m/1h/all)全部由"对桶求和"得到,成本是 O(窗口内的桶数),而不是回看所有历史包。
   - 同一份 1s 桶还直接喂给 IP 丢包热力图,数据只用存一份。
   - 桶推进是"按时间戳对齐尾桶",正常乱序很小的抓包是 O(1);乱序过多才退化到线性扫描,且有 10 分钟的保留窗兜底。

3. **上游聚合,别让 UI 跟着每个包抖**
   - 媒体流按 5s 采样聚合成历史点(吞吐量曲线、丢包增量),快照每 100ms 才发布一次,且**只在"包数或选中呼叫变化"时才真正重发**——空闲时零发布,CPU 空闲。
   - IP 页面的排序结果缓存 5s 刷新,不让丢包率数字每帧变化导致整张表上下乱跳。

4. **O(1) 的关联路径**
   - 包 → 流 → 呼叫全程哈希索引;RTP 关联走 `endpoint_call` 双查询,不进线性扫描。

5. **存储上对"原始报文"也设防**
   - `--raw-truncate N` 可以只保留每条 SIP 消息的前 N 字节,长时监控下把内存占用砍掉一大截(详情/诊断依旧完整)。

6. **部署形态**
   - 纯静态 musl 构建的单二进制,拷到抓包机上就能跑,不需要装运行时、不需要外部数据库,不依赖 PBX。`record` 模式还支持 `-d` 守护化 + pidfile,配合事件日志(`evlog`)可以"边录边丢原始 pcap",事后 `replay` / `export` 还原分析。

## 界面

TUI 一共 7 个页面,底部有 1-7 的 tab 条:`Tab`/`Shift-Tab` 连续切换:

- **Overview**:呼叫列表 + 摘要(ASR、平均 PDD/jitter/loss/MOS)
- **Search**:sngrep 风格的 Call-ID/号码/IP/SSRC 子串搜索
- **Call Detail**:固定四栏——左侧消息流(4/5)+ 诊断(1/5),右侧原始报文(2/3)+ 媒体流统计(1/3),双击即看某条消息原文
- **Heatmap**:按 IP 的丢包率时间热图
- **Streams / Event Log**:逐流统计、诊断事件流
- **IP Stats**:每个 IP 的 **进出方向(TX/RX)分开**的数量/字节/丢包率,按 `c` 可切到只看出/入丢包率的精简视图,`Enter` 下钻到该 IP 涉及的通话

## 快速上手

```sh
# 实时监控(所有网卡)
sipmon live -i any

# 只看 5060 端口
sipmon live -i eth0 -f "udp port 5060"

# 事后分析 pcap
sipmon file -r capture.pcap

# 或者直接把 pcap / evlog / jsonl 丢给默认模式
sipmon capture.pcap
```
